## 一、现状：现在到底靠什么算历史

**两条路，都从日志来：**

| 路径 | 机制 | 代价 |
|---|---|---|
| 运行期逐轮账本 | `session/event` → `recordTurn` 累加到内存 `folds`（会话 id → 四桶 + usd） | 只覆盖**进程活着期间**见过的轮次 |
| 历史回填 | 某个会话第一次被看到时 `backfillTurns` 走 `session.events`（退路 `eventAt(seq)` 逐条）把老轮次补进 `folds` | 每个会话一次 O(事件数)；**重启后每个会话都要重走一遍** |

**真机实测（刚重启后，当前会话）**：

```
pricing = { mode: "per-turn", turns: 115, coverage: 1, unpricedTurns: 0 }
measured.totalTokens = 24,150,455
cost.totalCny = ¥1.4571
```

也就是说：**回填跑到了，余额就是精确的**。现在的 `mixed/含估算` 只出现在回填拿不到事件的时候（访问器不可用、或某个会话在被看到之前不触发回填）。
结论：账本不是为了"修一个已经坏了的东西"，而是为了下面这三件事。

## 二、账本要解决的三件事（这是它存在的全部理由）

1. **重启后不再重走日志。** 现在每重启一次，每个会话都要把整份日志扫一遍（本机 74 个日志 / 3,363 轮 / 当时实测 1.75 s，但那是冷读；会话越长这个 O(事件数) 越难看）。账本让"第一次看到某会话"变成一次小文件读。
2. **冻结价格版本。** 这是最重要的一条。现在金额是**用当前价表重算**的：官方调价（我们踩过一次 V4-Pro 少算 3.3 倍的坑）会让**历史金额跟着变**。账本把「当时算出来的 usd」和「当时用的价目版本」一起落盘，历史就成了既成事实——调价只影响之后的轮次。
3. **历史可查。** 「按会话 / 按天 / 按模型」的明细不必再现场折叠日志（报告现在是全量折叠，本机 1.2 s，会话再多就线性变差）。

**明确不做**（避免偷偷扩大范围）：
- 不做跨机合并（Q2=A 已定，账本纯本机）。
- **不取代日志的权威地位**：日志仍是事实源，账本只是它的缓存与"当时价格的旁证"。
- 不做服务端/云端存储、不做多用户。

## 三、数据模型

**一行一个轮次**（`LedgerRow`）：

```jsonc
{
  "sessionId": "session-beb41318-…",   // 主键之一
  "seq": 1234,                          // 主键之二（事件序号）；(sessionId, seq) 幂等
  "time": 1758432000000,                // 该轮自己的时刻（毫秒）——峰谷判定用得到
  "model": "deepseek-flash",            // 该轮时点生效的模型
  "tier": "offpeak",                    // 当时判定的峰谷（便于回溯）
  "buckets": { "uncachedInputTokens": 96266, "cacheReadTokens": 6955648, "cacheWriteTokens": 0, "outputTokens": 67618 },
  "usdInput": 0.05, "usdOutput": 0.0319,// **写入时定价**，此后不再重算
  "priceVersion": "2026-09-18+override:e3b0c442",  // prices.json 的 generatedAt + 覆盖文件哈希
  "pluginVersion": "0.12.0"
}
```

**幂等键 = `(sessionId, seq)`**：重复写同一轮，读时后写覆盖（last-wins）。这样重放/回填/账本与实时事件交叠都不会重复计数——**这是账本唯一的正确性门槛**，验收脚本第一条就测它。

**文件布局**：

```
$DSH_HOME/storages/dsh-usage-card/
  prices-override.json            ← 已有
  ledger/
    2026-09.<pid>.jsonl           ← 按「轮次发生的月份」分文件，追加写；<pid> = 写它的进程
    2026-10.<pid>.jsonl
    index.json                    ← { schemaVersion, machineId, rows, bytes, lastWriteAt, months:[…] }
```

按**轮次发生的月份**分文件（不是写入时刻）：跨月回填不会写错文件，也不会出现"一个文件被追着改"。
本机量级：3,363 轮 × ~180 B ≈ 600 KB；一个月一个文件，几十到几百 KB。

**写入**：`recordTurn` 之后进内存缓冲，**防抖 300 ms** 或满 200 行落盘一次；用「追加 + 单行 JSON」原子写（`fs.appendFile`），崩溃最多丢最后一批（丢的是缓存，日志还在，下次回填即可重放）。
**读取**：需要某会话时，按月份文件扫 `sessionId` 命中行（或维护 `index.json` 里的会话→月份倒排）；命中即用**存储的 usd**，缺失的 seq 再走一段日志回填。

**与投影的关系**（不改口径纪律）：

```
投影四桶（实测、权威） − 账本覆盖的四桶 = 未覆盖部分 → 仍按当前档位线性估算，
仍如实标注 pricing.mode = mixed 与 coverage —— 账本只减少"未覆盖"的量，不粉饰它。
```

## 四、价格漂移：冻结之后要不要重算

账本冻结了金额，于是会出现一个必须回答的问题：**调价之后，老轮次的金额和"按今天价重算"对不上，要不要提示？**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 冻结为准，卡片不提示；报告里给一行「按当前价重算会是多少」的对照 | 多算一次全量（报告本来就在算） |
| B | 冻结为准，什么都不提 | 用户可能以为金额随价表走，调价后发现历史没变会疑惑 |
| C | 每次按当前价重算（账本只做加速，不冻结） | 回到今天的毛病：历史金额会随调价漂移，账本失去了第 2 条理由 |

## 五、回滚与安全

- 账本是**纯本地缓存**，删掉 `storages/dsh-usage-card/ledger/` 目录即回到今天的行为（卡片会重新走日志回填，金额口径不变）。
- 损坏不致命：坏行跳过、文件读不出就整份放弃该月并记一条 warn；**绝不因为账本读不出来就让卡片降级**。
- 账本里出现的只有 token 数与金额，**没有 prompt / 消息正文**——与插件的只读姿态一致。
- 写入路径只有一条（`recordTurn` 之后），不给任何路由开写接口：HTTP 面仍是只读（除手动同步那两条 POST）。

## 六、验收（先写判据，再写代码）

新增 `test/ledger-check.mjs`：

1. **幂等**：同一批轮次写两遍，读出来的汇总与写一遍完全一致（`(sessionId, seq)` 去重）。
2. **崩溃截断**：文件末尾留半行 JSON → 跳过该行、其余照常读出，且**不抛**。
3. **价格漂移**：把价表换一份，读出的历史金额不变；报告里的对照值随之变化。
4. **重启不重走日志**：假 ctx 跑 `apply` + 一次 backfill，断言第二次（模拟重启）读账本时**不再调用** `session.events` / `eventAt`（调用计数为 0）。
5. **与投影的关系不变**：账本覆盖 + 线性估算 = 投影四桶；`coverage` 如实反映覆盖比例。
6. **降级**：账本目录不存在 / 只读 → 卡片仍返回 `ok:true`，走今天的回填路径。

真机验收：改完重启，同一会话的 `cost.totalCny` 与改前**一致**（说明账本没有改变口径，只是不让它漂）；`pricing.mode` 仍是 `per-turn`。

## 八、A/B 机验证

**先讲一个事实差异**：W 机是**开发链接**（`profiles/web/node_modules/dsh-usage-card` → `vendor/` → 仓库，junction 链），改完即生效；A/B 机走的是**安装脚本**（`scripts/install-usage-card.ps1`，里面 `$src = 'github:Icstick/dsh-usage-card'`）——**从 GitHub 装**，所以它们的版本由远端提交决定。

步骤（每台机一遍）：

1. **确认设备与 profile**：目标机上每个要显示的 profile 各装一次（本机实测 3 个 profile）。
2. **更新到本次提交**：`pwsh -File install-usage-card.ps1`（脚本自带校验：`dependencies` / `bundles` / `lib/client.js` 三处齐了才算装好）。
   ⚠️ **预检**：`github:` 安装是按提交/引用解析的，版本号不变时可能命中缓存。所以**建议先 bump 到 0.12.0 再装**；否则要显式带 commit。
3. **重启该 profile 的 dsh**（宿主半改动必须重启；客户端半刷新即可）。
4. **三条判据**（与 W 机今天验的完全一致）：
   - `~/.dsh/settings.yaml` 的 `dsh-usage-card` 段出现 `fxSyncedRate` / `fxSyncedAt` / `fxSource`；

5. **记录机器标识**：`prices.json` 里的 `machineId` 目前留空未用（Q2=A 不合并，但仍建议填上，便于对账时区分）。

**通道**：W→A 走 SSH 公钥，W→B 走 cloud-server 跳板；长任务一律 `schtasks`（Windows OpenSSH 会在会话结束杀掉子进程树）。这些是既有的、踩过坑的路径，不新造。

**文件名带 pid（实现时补的决定）**：同一个 DSH_HOME 会被多个 dsh 进程共用（web / worker / headless 各起一份）。
两个进程同时往一个文件追加会互相插行，拼接出来的行解析失败就当坏行丢掉 —— 那是静默少算钱。按进程分文件后
这一类彻底不存在，且同一轮被两边各记一次也能在读时按 `(sessionId, seq)` 去重。文件读取按 (mtime, size) 判缓存，
所以别的进程刚写进去的行，本进程下一次读就看得见。

**刻意不做 index.json**：月份文件只有几个，全量扫描是几十毫秒；多一份索引就多一个可能与事实不符的第二真相源。
会话读取因此是"扫所有月份文件 + 命中过滤"，本机 3.4k 行量级完全够用。

## 十一、独立复核（2026-09-21，另一双眼睛）

按「不共享结论、只看 diff」的方式另派了一个审查者复看 afa8933..4f2926d。它翻出三条 P0，其中一条**实测复现**：

| # | 问题 | 处理 |
|---|---|---|
| P0-1 | 账本的「覆盖水位」直接取行里的最大 seq。混进一条 seq 异常但形状合法的行（改过 seq 语义 / 手工拼回旧 pid 文件 / 会话 id 复用）就让该会话**永远不再读日志**：真实轮次既不进账本也不被回填，金额静默少算（实测只剩正确值的 65%），卡片照常显示 | **修**：水位不许超过会话自己的 seq；超出的行既不当水位也不折进账，并记一条 warn。回归断言：塞一条 seq=999999 的行，日志必须照读、金额必须与干净账本一致 |
| P0-2 | rail（收起）态的环没有形状闸，宽态有 —— 两条路径护栏不对称，ok 为真但 measured 缺失时环会抛，由渲染边界兜成「渲染失败」（那一格白屏） | **修**：环复用同一道 payloadSane 闸，老实降级成空环；isolation 断言改成**宽窄分别断言**（原来把两态文本合并，才漏掉这一侧） |
| P0-3 | 报告「账本口径对照」把未定价轮按 0 记钱，差值方向恒为「账本更便宜」，会被误读成官方调价 | **修**：账本有未定价轮时不给差值，直接标「不可比」并说明原因 |

它同时确认了几件我改过的事（多进程分 pid 文件、dispose flush、turnKeys 上限、README 文件名），以及若干**未发现问题**的类别
（多进程并发追加 12000 行复现不出损坏、月份/时区一致、幂等与去重正确、路径穿越/日志注入/非 GET 全过、信任栅栏 fail-closed）。

它另外指出本地栅栏的一处言行不一：注释写「对端必须是回环」，代码却是「看得见才检查」（看不到 remoteAddress 就放行）。已改成 fail closed。
